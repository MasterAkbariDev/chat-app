# Frontend Plan — `legacy-frontend` (User Web App, Next.js)

Target: Next.js 15 App Router used properly (server layout for session, client islands for
interactivity), **TanStack Query** for all server state, a ~12-primitive design system replacing
the bespoke CSS, virtualized message feed, code-split heavy features. Web notifications are
**foreground-only** (Q9) — no service worker push.

Each phase depends on the matching backend phase's **contract being merged** (`Bn`).
Legend: Size S/M/L as in the backend plan.

---

## Status (2026-09-09) — read this before touching anything below

**2026-09-29: full UI/UX redesign, "Hearth" (supersedes "Modern Glassic" below).** Every screen was rebuilt on a
new solid-surface design system: no glass, blur or glow, and flush panels. Figtree/Bricolage/Vazirmatn type,
per-person colour identity, and 5 themes × light/dark with contrast-checked tokens and no first-paint flash. New
shared primitives: Dialog/ConfirmDialog with a focus trap and stack, Menu with right-click and long-press,
List, PageHeader, Switch and PasswordInput. See `../DESIGN_SYSTEM.md`. Behaviour and data flow are unchanged,
with these UX fixes:
- Conversations open at the first unread message or the newest one, and follow new arrivals.
- There's a jump-to-latest button with a new-message count, and messages are grouped by sender.
- Editing happens in the composer.
- Actions are keyboard, mouse and touch reachable.
- Chat rows are real links.
- The fake voice recorder and dead Archive button were removed.
- The open chat's list preview stays current.

`frontend-design/index.html` is no longer the visual source of truth. Lighthouse accessibility scores 100 on
all 12 audited routes (dev server).

**Visual redesign, "Modern Glassic":** the entire design system was rebuilt to match
`../frontend-design/index.html` + `figma-tokens.json` (a Figma-exported reference covering 16
screens — most still aspirational, see below) — glassmorphism (translucent, blurred surfaces
over two ambient drifting glow orbs, mounted once in `app/layout.tsx`), squircle avatars, and each
of the 5 themes now supports **both dark and light mode** (10 token sets total, `[data-theme]` +
`[data-mode]` on `<html>`, see `contexts/theme-context.tsx` and `app/globals.css`) — replacing the
old fixed-mode-per-theme system. `rose` replaced the old `midnightRose` key. Every screen that was
already wired to real data (auth, app shell/nav, chat list, conversation/messages, chat info,
new-conversation, settings, command palette) was re-skinned to this system and re-verified live
against the real backend; screens with no existing implementation (contacts book, global search,
packs/stickers/bot GUI, wallpaper studio, LiveKit calls, admin console) are **not** built yet —
that reference file's mockups for them are still just mockups. See `globals.css`'s `.glass-panel`
/`.glass-card`/`.glass-input`/`.glass-bar` for the reusable surface primitives, and their doc
comments for a real CSS-cascade-layers gotcha (Tailwind utilities can't override a property already
set by one of those classes — compose conditional/active states from plain Tailwind utilities
instead, not by layering a Tailwind override on top of a `.glass-*` class).

**Second design pass — floating glass, and search merged into the chat list:** every page-level
header and the message composer are no longer docked/flush bars; they're detached, absolutely-
positioned floating islands (`.glass-float` in `globals.css` — more opaque + a real drop shadow
than `.glass-panel`/`.glass-bar`, since it needs to read as elevated *above* scrolling content
behind it) with a visible gap to the container edge so the ambient glow shows around them. Applied
to: `ChatHeader` (softly rounded, `rounded-[24px]`) and `Composer` (fully `rounded-full`, plus a
separate floating pill for the reply-preview/recording states) in `ConversationView`; the chat
list's own title+search+folder bar; `ChatInfoPanel`, Settings, and Contacts page headers; `NavRail`
(now a detached floating vertical island, not a flush left rail) and `BottomNav` (a floating
rounded-full pill, matching the composer). In every case, the scrollable content beneath fills its
container edge-to-edge (`absolute inset-0 overflow-y-auto`) with top/bottom padding sized to clear
the floating bar(s), rather than the old flex-column (header → flex-1 scroll → footer) layout.
**Global search is no longer a separate page** — `/app/search` is gone; real cross-scope search
(`GET /v1/search`, all three scopes) is merged directly into the chat list itself
(`GlobalSearchResults.tsx`), surfaced by typing in the same search box that sits above the
folder-tabs row — which swaps to scope tabs (People/Channels/Messages) once a query is active,
then back to folder tabs when it's cleared. `NavRail`/`BottomNav` no longer have a Search
destination for the same reason.

**Backend pivot, superseding everything in the previous status box below this line's history:**
this frontend now talks **exclusively to `chat-app/backend`** (the refactored NestJS backend,
phases B0–B12, all done per `../BACKEND_PLAN.md`) — **not** the original `legacy-chat` repo. That
old backend has been stopped and is not to be run alongside this one; don't add code that assumes
its contract. `chat-app/backend`'s checked-in `openapi.json` is stale (confirmed: it documents
zero `/v1` paths despite ~20 being live) — every type in `frontend/src/lib/api/types.ts` was
verified by reading the backend's own DTO/service/schema source plus direct `curl` testing against
a running instance, not generated from that file.

Everything below the quirks list further down is the **original aspirational plan**, written
before either backend existed in its current form — treat any remaining `/v1/...` path, route, or

**Confirmed backend quirks worth knowing before wiring anything else** (found by reading
`chat-app/backend`'s actual source and, for the ambiguous ones, verified empirically against a
running instance — full detail in `frontend/src/lib/api/types.ts` and `lib/socket.ts`'s doc
comments):

- CORS is a **strict, exact-match allowlist** (`CORS_ORIGIN` env var, no wildcard, fails closed at boot if unset) — shared by HTTP, the socket gateway, and `/uploads`. A dev frontend on a port that isn't in the list gets a same-looking-as-network-failure `ERR_FAILED` on every request with no explanation in the response; check `CORS_ORIGIN` in `backend/.env` first if requests start failing after `preview_start` picks a new `autoPort`.
- `/auth/register` is throttled to **3/hour per IP**, backed by Redis (survives a backend restart, unlike an in-memory throttler) — easy to exhaust while manually testing signup flows repeatedly.
- Reactions (`POST /messages/:id/reaction`) return a **delta**, not a full message: `{channelId, messageId, emoji, packItemId, userId, action, reactions}` — exactly one of `emoji`/`packItemId` is non-null (2026-09-09: a reaction can be a sticker/animated-emoji pack item, not just a plain emoji; see F5). The `reaction_changed` socket broadcast carries the same `emoji`/`packItemId` plus `relativePath`/`packId` (populated only on `action: "added"`) but still no full `reactions` array — the frontend replays the add/remove locally against the cached array, keyed by `emoji ?? packItemId`, for that event.
- `GET /v1/messages/:id/reads` ("seen by") is **author-only** and **per-message** — there's no cheap way to show a read tick on every own message; only the newest one is fetched.
- **`message_updated`'s broadcast doesn't reliably reach the acting user's own socket** for pin/unpin (and, defensively, edit/react are patched the same way) — confirmed: DB update is correct, other connected clients see it, the actor doesn't until a refetch. The frontend patches the query cache from the mutation's own HTTP response for the actor; the broadcast still carries it to everyone else. One isolated case of the broadcast also missing a *different*, non-acting connected client for a pin was observed during testing but did not reproduce on a repeat (edit's broadcast reached that same client fine) — worth remembering as a known flake class, not yet root-caused.
- Auth guards are per-route (`@UseGuards(JwtAuthGuard)`), not global — a new endpoint that forgets it is silently public.
- **Two different error response envelopes are live, not one**: most controllers (including all of auth) fall through to Nest's default `{message, error, statusCode}`; any controller with `@UseFilters(AllExceptionsFilter)` (confirmed: contacts, search, channels) instead returns `{error: {code, message}}`. `client.ts`'s `apiFetch` now checks both shapes — don't revert it to checking only `parsed.message`, or contacts/search error messages silently degrade to a generic HTTP status string.
- `GET /v1/search?scope=channels` is **not membership-scoped** — it can surface public groups/channels the caller hasn't joined at all (only DMs, Saved Messages, and soft-deleted chats are excluded by its `type` filter). The merged search UI (`GlobalSearchResults.tsx`) treats "not in my already-loaded channel list" as "not joined" and offers a Join button (`POST /chats/subscribe`) rather than Open.
- `GET /v1/contacts` never returns `phoneNumber`/`email`, mutual contact or not — that reveal only happens on `GET /users/by-id/:userId` (gated on `areMutualContacts`), a separate call the contacts list doesn't make automatically.
- `POST /v1/contacts`'s identifier fields (`userId`/`username`/`phone`/`email`) are each individually optional in the DTO — "exactly one must be present" is enforced only in the service (400 if 0 or 2+), invisible in the OpenAPI schema. `/app/contacts`'s add form enforces it client-side too (one tab active at a time) to avoid a pointless round trip.

`.github/workflows/ci-cd.yml`: on every push/PR, runs the backend's and frontend's real
typecheck/lint/test/build jobs; on a push to `main` specifically, once those pass, SSHes into a
configured server and runs `docker compose up -d --build app frontend`. Also added: a
`frontend/Dockerfile` + `.dockerignore` (Next.js standalone-output production image — needed
`output: "standalone"` added to `next.config.ts`) and a matching `frontend` service in
`backend/docker-compose.yml`, since only the backend had a Dockerfile before this. The Dockerfile
was actually built locally (`docker build`) to confirm it works, not just written and assumed.

This can't be finished by an agent alone — it needs a server, a domain, and secrets only a human
has. **Full step-by-step setup instructions are in `docs/DEPLOYMENT.md`**: putting this repo on
GitHub (it isn't one yet), preparing the server, generating a deploy-only SSH key, and the exact
five GitHub repo secrets (`DEPLOY_HOST`/`DEPLOY_USER`/`DEPLOY_SSH_KEY`/`DEPLOY_PORT`/`DEPLOY_PATH`)
the workflow reads.

**New (2026-09-27): the app/frontend HTTP port is configurable, with a real fallback chain, not
just a hardcoded default.** Two optional repo *variables* (`DEPLOY_APP_PORT`/
`DEPLOY_FRONTEND_PORT`, deliberately not secrets — a port isn't sensitive) let you pin the port; if
unset, the deploy script auto-detects whatever port that container is **already** published on
(`docker compose port app 3000`, same for `frontend`) and reuses it, so a redeploy can never
silently move the app to docker-compose.yml's bare default out from under a reverse proxy already
pointed at it — only falling through to that default on a genuinely first-ever deploy. The
port-extraction (`awk -F: '{print $NF}'`, robust to both IPv4- and IPv6-style
`docker compose port` output) was verified against a real running container, and all three
resolution paths (pinned / auto-detected / first-deploy-fallback) were dry-run separately to
confirm the precedence is actually right, not just written to look right.
